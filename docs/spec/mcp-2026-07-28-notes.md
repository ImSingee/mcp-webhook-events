来源：`modelcontextprotocol/modelcontextprotocol` 仓库 `main` 分支
`docs/specification/2026-07-28/**` 与 `schema/2026-07-28/schema.ts`（2026-10-29 抓取），
对应站点 `https://modelcontextprotocol.io/specification/2026-07-28/...`。
引号内为原文，其余是为本项目整理的要点。

## 1. basic（`basic/index.mdx`）

- 请求 `id` 为 string 或 integer，**不能是 null**。
- 每个 result **必须**带 `resultType`；普通结果为 `"complete"`。
  客户端对缺失的 `resultType` 视为 `"complete"`（兼容旧服务端）。
- 错误码分区：
  - `-32000`～`-32019`：legacy，新实现 SHOULD NOT 使用。
  - `-32020`～`-32099`：保留给 MCP 规范，实现 **MUST NOT** 发出规范未定义的码。
  - 已定义：`-32020` HeaderMismatch、`-32021` MissingRequiredClientCapability、`-32022` UnsupportedProtocolVersion。
  - SEP-3415 申请的 `-32023`～`-32027`（NotFound/Forbidden/ResourceExhausted/Unsupported/CallbackEndpointError）尚属草案编号（“provisional until then”）。
  - 本地错误（例如 SDK 超时）“should ensure they cannot be mistaken for errors received from the peer”。
- **无状态**：“Servers MUST NOT rely on prior requests over the same connection to establish context”。每个请求在 `_meta` 中携带：

  | key | 必填 |
  |---|---|
  | `io.modelcontextprotocol/protocolVersion` | 是 |
  | `io.modelcontextprotocol/clientInfo` | 否（SHOULD） |
  | `io.modelcontextprotocol/clientCapabilities` | 是 |
  | `io.modelcontextprotocol/logLevel` | 否（已废弃） |

  “A request missing any required field is malformed; the server MUST reject it with JSON-RPC error code `-32602` (Invalid params). On HTTP, the response status MUST be `400 Bad Request`.”
- 服务端 SHOULD 在每个 result 的 `_meta` 中带 `io.modelcontextprotocol/serverInfo`。
- 订阅流上的每条通知 MUST 带 `_meta["io.modelcontextprotocol/subscriptionId"]`，值是打开该流的请求 id。
- `_meta` key 前缀第二段为 `modelcontextprotocol` 或 `mcp` 的保留给 MCP。

## 2. Streamable HTTP（`basic/transports/streamable-http.mdx`）

- 单一 MCP endpoint，只接受 **POST**。每条客户端消息是一个独立的 POST。
- 客户端 MUST 发送 `Accept: application/json, text/event-stream`。
- body 是单个 JSON-RPC request 或 notification；客户端 MUST NOT 发送 response。
- notification：接受时返回 `202 Accepted` 无 body；不接受时返回 4xx，body MAY 是无 id 的 JSON-RPC error。
  “This revision of the core protocol defines no client-to-server notifications over Streamable HTTP … header requirements for notification POSTs are not defined by this revision.”
- request：返回 `application/json` 单个对象，或 `text/event-stream`。SSE 流里可以先发与该请求相关的 notification，最后发 response，response SHOULD 结束该流。
- 发起 SSE 时 SHOULD 带 `X-Accel-Buffering: no`。
- 长连接流（如 `subscriptions/listen`）鼓励周期性发送 SSE 注释行作为 keep-alive。
- “Resumable SSE streams via `Last-Event-ID` are not supported.”
- **Origin**：“Servers MUST validate the `Origin` header … If the `Origin` header is present and invalid, servers MUST respond with HTTP 403 Forbidden.”
- **取消**：“Closing the SSE response stream MUST be treated by the server as cancellation of that request.”
- **请求元数据 header**：
  - `MCP-Protocol-Version` 每个 POST 都 MUST 带，且 MUST 等于 `_meta` 中的 protocolVersion，否则 `400` + `HeaderMismatch(-32020)`。
  - 版本不支持：`400` + `UnsupportedProtocolVersionError(-32022)`，`data: {supported:[…], requested}`。
  - 方法不支持：“it MUST respond with `404 Not Found` and a JSON-RPC error with code `-32601`”。
  - 不支持 2025-06-18 之前的客户端时，缺少该 header 的请求按 Server Validation 拒绝（400 + -32020）。

  | Header | 来源 | 必需于 |
  |---|---|---|
  | `Mcp-Method` | `method` | 所有请求 |
  | `Mcp-Name` | `params.name` 或 `params.uri` | `tools/call`、`resources/read`、`prompts/get`（SEP-3415 追加 `events/poll|stream|subscribe|unsubscribe`） |

  - 不能安全表示为 ASCII header 的值用 `=?base64?{Base64}?=` 哨兵格式；与哨兵模式碰撞的纯 ASCII 值也必须编码。服务端比较前 MUST 解码。
  - header 名大小写不敏感，值大小写敏感。
  - **Server Validation**：缺少必需的标准 header、header 与 body 不一致、header 含非法字符 → `400 Bad Request` + `-32020`。
- **向后兼容**：只支持本版本的服务端收到旧流量时 SHOULD：GET/DELETE → `405`；忽略 `Mcp-Session-Id`、不签发；忽略 `Last-Event-ID`。
  双版本客户端先发 modern 请求，收到 400 时看 body 是否为可识别的 modern JSON-RPC 错误，否则回退到 `initialize`。

## 3. server/discover（`server/discover.mdx`）

- “Servers MUST implement it.” 请求只有标准 `_meta`。
- 结果：`resultType`、`supportedVersions`、`capabilities`、`_meta["io.modelcontextprotocol/serverInfo"]`（SHOULD）、`instructions`（可选），并且 `DiscoverResult extends CacheableResult`，即 `ttlMs`、`cacheScope`（`"public"|"private"`）为必填字段。
- `ServerCapabilities.extensions`：extension id → settings object（空对象表示支持且无设置）。

## 4. Versioning（`basic/versioning.mdx`）

- 没有握手；每个请求声明版本，服务端逐个接受或拒绝。
- 双版本服务端：带 modern `_meta` 的请求按本版本无状态处理；`initialize` 选择 legacy 语义。“A dual-era server MAY serve both eras concurrently on the same endpoint”。
- 扩展协商：`capabilities.extensions`。“If one party supports an extension but the other does not, the supporting party MUST either revert to core protocol behavior or reject the request with an appropriate error.”
- 只支持 modern 的服务端 SHOULD 在 `initialize` 的错误里列出支持的版本。

## 5. Subscriptions（`basic/patterns/subscriptions.mdx`）

- `subscriptions/listen` 请求 `params.notifications` 为过滤器：`toolsListChanged`、`promptsListChanged`、`resourcesListChanged`、`resourceSubscriptions`（SEP-3415 追加 `eventsListChanged`）。服务端 MUST NOT 发送未请求的类型。
- 第一条消息 MUST 是 `notifications/subscriptions/acknowledged`，`params.notifications` 为服务端同意的子集，`_meta` 带 subscriptionId。
- 服务端主动结束时 SHOULD 发送 `{"resultType":"complete","_meta":{"io.modelcontextprotocol/subscriptionId":<id>}}` 作为最终 response。

## 6. Cancellation（`basic/patterns/cancellation.mdx`）

- HTTP：关闭 SSE 响应流即取消，不需要 `notifications/cancelled`。
- stdio：客户端 MUST 发送 `notifications/cancelled {requestId, reason?}`。服务端 SHOULD 停止处理、释放资源、不再回复。
- 未知 id、已完成的请求、格式错误的取消通知 SHOULD 被忽略。

## 7. Tools（`server/tools.mdx`、`schema.ts`）

- `tools/list` 结果 `ListToolsResult extends PaginatedResult, CacheableResult`：`tools`、可选 `nextCursor`、必填 `ttlMs`、`cacheScope`。SHOULD 按确定顺序返回。
- `Tool`：`name`、`description`、`inputSchema`（根 MUST `type:"object"`）、可选 `outputSchema`、`annotations`、`_meta`。
- `CallToolResult`：`content[]`、可选 `structuredContent`、`isError`。
- 未知工具、请求格式错误 → JSON-RPC 错误 `-32602`；工具执行错误（参数校验、业务错误）→ result 中 `isError:true`。

## 8. Changelog 中与实现相关的点（`changelog.mdx`）

- 删除 session、`Mcp-Session-Id`、GET 流、`initialize`/`notifications/initialized`。
- **删除 `ping`**、`logging/setLevel`。本项目据此把 modern 请求中的 `ping` 当作未知方法，返回 `404` + `-32601`；只有 legacy（2025-06-18 / 2025-11-25）路径仍回应 `ping`，因为那两个版本定义了它。
- 所有 result 必带 `resultType`。
- 删除 SSE 可恢复性（`Last-Event-ID`）。
- DCR 被标记为 deprecated（仍为 MAY），推荐 CIMD。

## 9. Authorization（`basic/authorization/*.mdx`）

- MCP server MUST 实现 RFC 9728 Protected Resource Metadata；`authorization_servers` 至少一项。
  发现方式之一：401 的 `WWW-Authenticate` 中带 `resource_metadata`；或 well-known：`/.well-known/oauth-protected-resource/<mcp path>` 与根路径 `/.well-known/oauth-protected-resource`。
- AS MUST 提供 RFC 8414 或 OIDC Discovery 之一；客户端按序尝试 `/.well-known/oauth-authorization-server`、`/.well-known/openid-configuration`，并 MUST 校验 `issuer` 与构造 URL 所用 issuer 完全相同。
- PKCE：客户端 MUST 用 S256；AS 元数据缺少 `code_challenge_methods_supported` 时客户端 MUST 拒绝继续。
- RFC 8707：客户端 MUST 在授权请求和 token 请求中都带 `resource`（MCP server 的 canonical URI）；服务端 MUST 校验 token 是为自己签发的（audience）。
- RFC 9207：AS SHOULD 在授权响应（含错误响应）中带 `iss`，带了就 MUST 在元数据中声明 `authorization_response_iss_parameter_supported: true`；客户端 MUST 在兑换 code 前校验 `iss`（简单字符串比较，不做规范化）。
- token MUST 放在 `Authorization: Bearer`，不能放 query。无效或过期 token → `401`；scope 不足 → `403` + `insufficient_scope`。
- 401 SHOULD 带 `scope`；服务端不应在 scope 中包含 `offline_access`。
- 对 public client，AS MUST 轮换 refresh token（OAuth 2.1 §4.3.1）。
- 通信安全：AS 端点 MUST HTTPS；redirect URI MUST 是 `localhost` 或 HTTPS。
- Open redirection：AS MUST 精确匹配已注册的 redirect URI。
- DCR（RFC 7591）：deprecated，MAY 支持；客户端 MUST 指定 `application_type`（native/web）。
- Localhost redirect：AS MUST 清楚展示 redirect URI 的 hostname，SHOULD 对仅 localhost 的回调额外提示。
- 客户端凭据按 `issuer` 绑定，AS 变化时 MUST 重新注册。
